# Runtime assembly and `f16` backend questions

Research for Q2/Q3 in `docs/02-ir-design.md` §16. Local source observations refer to `/home/su3h7am/Projects/Odin` (the fork checkout); upstream links identify the published history. The checkout also contains later fork-only Linux no-CRT work, identified separately below.

## Q2 — runtime assembly and `-no-crt`

### Origins, authors and reasons

- The no-CRT path for Linux was introduced by [PR #1671](https://github.com/odin-lang/Odin/pull/1671), “Make no crt work on Linux,” merged by Ginger Bill on 2022-03-30. The PR author was colrdavidson; commit `abf0fd7`. The PR supplied no description. The author explicitly cautioned that it did not make Odin fully standalone: users still needed to link something providing `_start` and remaining libc hooks; it helped the ongoing Linux libc burndown. Bill replied “I'll merge it any way.” This is the documented reason, not a claim that it completed a freestanding runtime.
- The Linux amd64 startup stub `base/runtime/entry_unix_no_crt_amd64.asm` was introduced in commit [`2e66d621`](https://github.com/odin-lang/Odin/commit/2e66d621b50965624f244a77661bcd0225cfdfd5), authored by flysand7 (2023-10-22), “Implement -no-crt entry point on linux.” It is selected by `base/runtime/entry_unix.odin` for `ODIN_NO_CRT`; it establishes the process entry and transfers argc/argv to `_start_odin`. It is an assembly object because the OS entry point has to establish the language entry call at the raw process entry boundary.
- Current fork-only additions are not upstream PRs: local commit `d8d3fcb` (“Bootstrap main-thread TLS in Linux no-CRT entry stubs,” Su3h7aM) adds startup TLS setup; `9568112` (“Share Linux no-CRT TLS layout between startup and worker threads,” Su3h7aM) shares that layout; and `0979a72` (“Support stack protectors in Linux no-CRT runtime,” Su3h7aM) adds stack-protector support. Their commit messages state the functional reason. The current fork’s runtime imports the corresponding architecture-specific sources in `base/runtime/tls_linux_no_crt.odin` and `base/runtime/stack_protector_linux_no_crt.odin`. These local additions should not be presented as upstream history.
- Later platform support reflects tool availability rather than a claim that assembly is intrinsically required: fork commit `0a79cc9` adds the Linux arm64 entry and says it fixes `-target:linux_arm64 -no-crt` plus wrong cross-assembly with host `as`. Upstream PR [#6784](https://github.com/odin-lang/Odin/pull/6784), by lualvsil, added AArch64 foreign-assembly support because NASM is x86-only, using clang for arm64.

### How the official compiler handles it

`foreign import` of an assembly source is a request for the compiler’s linker stage to assemble the file; it is not an inline-assembly feature. In the current fork, `src/linker.cpp:263` onward implements `linker_assemble_asm_input`. It chooses NASM for x86 (`nasm`/`ODIN_NASM_PATH`), clang for ARM64 and RISC-V (`clang`/`ODIN_CLANG_PATH`, with target flags), and system `as` for the other supported architecture/OS branch; extra flags come from `-extra-assembler-flags`. The AArch64 PR confirms the NASM limitation and clang choice. The source also has Linux executable-stack-note handling. LLVM is used for the compiler backend, but does not assemble these `.asm` foreign imports; no use of `llvm-mc` was found in this path. `build_settings.cpp` stores `extra_assembler_flags` (`src/build_settings.cpp:563` in this checkout).

The `-no-crt` mechanism is broader than these stubs: it disables automatic C runtime linkage and changes runtime/entry behavior. The architecture/platform entry selection is visible in `base/runtime/entry_unix.odin`; the stubs are only selected in relevant `when` branches. Linux amd64/arm64/RISC-V have Linux-specific entry/TLS/stack-protector files in this fork; generic Unix also has amd64, i386, RISC-V, and Darwin arm64 entry stubs. Darwin, BSD and Windows have their own runtime/platform startup paths; do not assume the Linux TLS layout or syscall conventions port. Windows uses its native startup/runtime and has its own assembly uses; Darwin’s `-no-crt` entry source is specifically arm64 in the Unix entry selector. The official linker’s assembler selection is OS/architecture-specific, so a portable replacement must preserve those distinctions.

### Ginger Bill’s position and recommendation

Ginger Bill’s [comment on issue #4444](https://github.com/odin-lang/Odin/issues/4444) says assembly can be imported with `foreign import` and built with NASM. He described assembly support as planned, while explicitly not committing to a design; he weighed string-template and parsed-block inline asm against an assembly-only pseudo-procedure that understands Odin types. He also noted architecture guarding. This is not a statement that runtime `.asm` should be rewritten in Odin, nor a specific endorsement of naked procedures. His 2021 [discussion #955](https://github.com/odin-lang/Odin/discussions/955) is an incomplete proposal for templated inline asm with explicit operands/clobbers, not an endorsed solution for naked startup code. Naked procedures existed as an Odin calling convention, but they do not themselves provide assembler syntax or guarantee all special entry constraints.

**Recommendation:** have the compiler emit the tiny process-entry sequence directly for each initially supported target, where that is simpler than creating and assembling a foreign source file. For the remaining small runtime stubs, keep the existing assembly as the reference behavior initially; do not embed a second general-purpose assembler solely to support these files. `core:rexcode` is the prior art for instruction encoding and is the sensible reuse if later work needs to encode the small fixed instruction sequences in compiler-owned code. It is not, by itself, a complete source assembler, relocation/object writer, or cross-platform startup abstraction. Avoid a blind port to ordinary/naked Odin procedures: a naked convention is useful only when compiler semantics guarantee exact register/stack preservation and the body can express target instructions. Revisit these stubs individually once the compiler has an Odin-level encoding path; preserve per-target startup, TLS, and stack-protector behavior.

## Q3 — `__ODIN_LLVM_F16_SUPPORTED`

### Definition, history and target values

The definition site is `src/checker.cpp:1519–1527` in the fork: it starts `f16_supported = true`, sets it false for `is_arch_wasm()`, and also false for `darwin_amd64`, then publishes the compile-time boolean `__ODIN_LLVM_F16_SUPPORTED`. Thus the observed matrix is **false** for all wasm targets and Darwin/amd64; **true** for other target combinations handled by this checker. This is not a general LLVM version test in the current source (the nearby comment says LLVM 17/new pass system is the baseline).

The feature switch and runtime alias were introduced upstream by Ginger Bill’s commit [`96fbafe`](https://github.com/odin-lang/Odin/commit/96fbafe3598822d8d62791d881879c4da33431ea), “Update ABI breaking changes for `f16` types (due to LLVM 15+),” 2023-09-21. `src/checker.cpp` initially derived the bool from whether the new pass system was in use; `base/runtime/internal.odin` introduced `__float16 :: f16 when __ODIN_LLVM_F16_SUPPORTED else u16`. The reason stated in the commit is LLVM-15+-related `f16` ABI changes; the runtime uses this alias at compiler-runtime helper boundaries.

The later target exception is upstream [issue #3222](https://github.com/odin-lang/Odin/issues/3222) / [PR #3329](https://github.com/odin-lang/Odin/pull/3329), authored by laytan and merged by Ginger Bill (2024-03-25). On Intel macOS with LLVM 17, generated `__extendhfsf2` calls put the half argument in `edi` and expect f32 back in `xmm0`; making the runtime helper boundary integer-shaped fixed the failure. PR discussion says those calls occur on older microarchitectures (pre-Haswell); Windows/Linux generated a different convention in the tested case. The `darwin_amd64` false setting makes the runtime’s helper ABI match this behavior. Wasm is explicitly false in the compiler source; the checked history does not establish a separate bug/rationale for that target, so its specific rationale is unknown here.

### What is observable

The switch does **not** change Odin’s `f16` language type into `u16`. `f16` remains a 16-bit IEEE binary floating-point value; `size_of(f16)`, its two-byte storage, and the bit pattern exposed through `transmute`/bitcast are user-observable and must remain correct. Its implementation representation is software-emulated on targets without native backend support, but those semantics cannot be changed by a non-LLVM backend.

The switch does affect runtime helper procedure signatures and therefore their ABI. `base/runtime/internal.odin` routes f16 conversions through software routines (`f32_to_f16`, `f16_to_f32`) and exports names including `__truncsfhf2`, `__truncdfhf2`, `__extendhfsf2`, `__gnu_f2h_ieee`, and `__gnu_h2f_ieee`; ARM EABI also has `__aeabi_d2h`. The `__gnu_*` spellings are compatibility/linkage symbol names, not a dependency on GNU libraries. Current runtime comments note that on arm32 these helper calls use core-register integer-shaped arguments/results, unlike ordinary AAPCS-VFP floating arguments; see `base/runtime/internal.odin` near `__f16_abi` and the helper declarations. Foreign C interop is observable too: an Odin `f16` passed across a C boundary must use the target C ABI for `_Float16`/`__fp16` where supported, rather than infer that the internal runtime alias determines all user ABI behavior. The LLVM-specific switch only governs these compiler-runtime helper types/calls.

### Requirement for a non-LLVM backend

Report the value that makes the runtime helper signatures and generated helper calls agree. If the backend lowers runtime `f16` helper boundaries as 16-bit integer/core-register ABI values (or cannot represent LLVM’s `half` helper ABI), publish **false** and retain the software bit-conversion implementation. Publish **true** only if the backend can use and correctly call the matching native `f16` helper ABI for that target. Do not hard-code false merely because the backend is not LLVM: the property is target/backend ABI compatibility, not language-level `f16` support. Separately implement the platform’s actual foreign-C `f16` ABI and keep size, storage, conversion, and bit patterns invariant.
